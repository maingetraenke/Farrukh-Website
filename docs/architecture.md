# Architecture

## Stack

- **Next.js 16** (App Router, Turbopack, TypeScript strict) — `apps/web`
- **Tailwind CSS v4 + shadcn/ui** (style: `radix-nova`) for the design system
- **Supabase**: Postgres, Auth, Row Level Security, Storage
- **React Hook Form + Zod** for form validation
- **TanStack Table** for data grids (Phase 2+)
- **React-PDF** for server-generated PDFs (Phase 4)
- **Resend** for transactional email (Phase 4)
- **Vitest** (unit/integration) + **Playwright** (E2E)
- **pnpm** workspaces, single app (`apps/web`) today; the workspace exists
  so a second app (e.g. a public ordering site, Release 1.1) can be added
  without restructuring.

Next.js 16 is a genuinely new major version relative to most training data
and tutorials — see `apps/web/AGENTS.md` (imported into `apps/web/CLAUDE.md`)
before writing App Router code. The two changes that shaped this codebase:

- **Async Request APIs**: `cookies()`, `headers()`, `params`, `searchParams`
  are all `Promise`s now (no sync compat mode). See `lib/supabase/server.ts`.
- **`middleware.ts` → `proxy.ts`**: `src/proxy.ts` (not `middleware.ts`)
  refreshes the Supabase session cookie on every navigation.

## Layering

UI (`src/app/**`, `src/components/**`) → domain (`src/lib/domain/**`) → data
access (`src/lib/supabase/**`, Server Actions, Route Handlers). Business
rules live in the domain layer or in Postgres (constraints, RLS, triggers),
never only in a client component — see CLAUDE.md rule 3.

- `src/lib/domain/` — pure functions (money math, validation) with no I/O,
  easy to unit test. `money.ts` is the first example (Phase 1).
- `src/lib/supabase/` — `client.ts` (browser), `server.ts` (Server
  Components/Actions/Route Handlers), `types.ts` (hand-written Database
  type until the project is linked to a real Supabase project — see the
  comment at the top of that file for the regeneration command).
- `src/lib/auth/` — `session.ts` (`getCurrentUser`/`requireUser`/
  `requireRole`, the server-side permission gate every protected
  page/layout goes through) and `actions.ts` (sign-out Server Action).
- Status transitions (order status, invoice finalization, payment
  status, ...) go through a domain service function once those features
  land (Phase 2+) — never a raw `update()` call from a component. See
  CLAUDE.md rule 10.

## Multi-tenancy & permissions

Single Postgres schema, tenant-scoped by `organization_id` on every
business table, enforced by Row Level Security — see `docs/database.md`
for the policy pattern. `profiles.role` (`ADMIN`, `DISPOSITION`, `LAGER`,
`FAHRER`, `BUCHHALTUNG`) drives both:

1. **RLS policies** (`public.has_role(...)`, `public.is_admin()` SQL
   helper functions) — the actual security boundary.
2. **UI/nav visibility** (`src/lib/nav.ts`) and **route-level gates**
   (`requireUser`/`requireRole` in `src/lib/auth/session.ts`) — for a
   coherent UX, not a substitute for RLS.

Never trust the client-side role check alone; RLS is what actually
prevents a FAHRER session from reading purchase prices, for example.

## Money, numbering, audit

- **Money** is always an integer count of cents (Postgres `integer`
  columns, TypeScript `number` treated as an integer — never `numeric`
  cast to JS float, never a fractional-euro field). See `money.ts` and
  CLAUDE.md rule 9.
- **Document numbers** (`MG-K-000001`, `MG-B-2026-000001`, ...) are
  generated by `public.next_sequence_value()`, an atomic Postgres upsert —
  never `SELECT count(*) + 1` from application code. See
  `docs/database.md#numbering`.
- **Audit log** (`audit_logs`) is written by domain services for
  price/stock/status/role/settings changes, not by blanket database
  triggers, since a meaningful audit entry ("order status DRAFT →
  CONFIRMED") is usually richer than a raw row diff. Phase 1 ships the
  table and RLS; the first writers land alongside Phase 2 order flows.

## Deployment

Vercel, connected to the Supabase project via environment variables (see
`.env.example`). No secrets are committed; `.env.local` in `apps/web` is
gitignored.

## Repo structure

```
apps/web/src
  app/                  App Router routes
    (app)/              Authenticated shell (sidebar/topbar), one folder
                         per nav item (dashboard, customers, products, ...)
    login/               Public login route
  components/
    ui/                  shadcn/ui primitives (generated, don't hand-edit
                         beyond what `shadcn add` produces)
    app-shell/           Sidebar/topbar
    dashboard/           Dashboard-specific widgets
  lib/
    auth/                Session/role helpers, Server Actions
    supabase/            Client factories + hand-written Database type
    domain/              Pure business logic (money, later: pricing,
                         inventory, numbering helpers used from Server
                         Actions)
    nav.ts               Nav item ↔ role mapping
  proxy.ts               Session-refresh proxy (Next 16's middleware)
supabase/
  migrations/            SQL migrations — the only way schema changes
  seed.sql                Phase 1 demo data (brands, no invented prices)
tests/
  unit/                  Vitest, pure functions
  integration/            Vitest, future: exercised against a local
                         Supabase instance
  e2e/                    Playwright
docs/                    This file, database.md, implementation-plan.md
```
